## 失败与设计目标

已观察到的缺口包括没有读取所需机制证据，以及把充分条件写成必要条件。答案结构和
引用 ID 合法并不能发现这些问题。本实验让拟发布答案经过一次独立生成调用，要求给出
问题覆盖项、每段支持度和条件范围的证据依据。模型复核仍可能出错，不能代替独立评估。

## 开关与兼容性

服务和对照 CLI 使用 `--agent-review-answers`，默认关闭。关闭时保持原有动作提示词、
输入和终态；同一生成器配置下保持原 Agent profile 指纹，新复核提示词和合同只进入
启用配置的指纹。本轮另修正传输重试策略，其版本会改变 off/on 两侧的生成器及 Agent 指纹。
单轮 RAG/固定工作流不启用此机制。追问和无答案返回保留原有直接终止行为。

## 状态与预算

1. `answer` 先按原有结构/引用合同解析。启用复核时，非空答案仅存为请求内草稿，不发布。
2. 下一模型调用检查该草稿。输入只含问题、草稿和已读取的完整证据，不含未读候选正文。
3. 问题覆盖和各段支持/条件范围均通过才发布。首次不通过，将有界复核反馈交回调查流程，
   允许使用剩余搜索/读取额度补证据或修改表述。
4. 最多再提交一个修订草稿并复核；第二次不通过以 `invalid_answer` 结束，不发布草稿。
   复核 JSON 无效也以 `invalid_answer` 结束，不自动修理 JSON。

所有生成调用共享 `max_steps`、累计输入 token、单次上下文和时长限制；一次通过需额外
一次模型调用，发生补救时最多两次复核调用。补查和重写仍占用原有决策/工具额度。
预算不足、超时、生成失败、取消沿用既有终态；在依赖调用边界检查，不能强杀进行中的
网络请求。补救阶段仍可决定追问或拒答。下一次答案必须重新复核，不能继承旧草稿的通过状态。

## 复核合同

`answer-evidence-review-v1` 返回固定三部分：

- `coverage`：非空的问题覆盖项，每项有 requirement、covered 和 evidence_ids。
- `blocks`：草稿每段恰好一项，包含 block、supported、condition_scope_supported、
  evidence_ids 和 finding。该段任一陈述不被支持即不能整体通过。
- `suggested_queries`：至多两个补查建议，仅作为不可信反馈数据，不直接执行。

正向覆盖所列证据必须出现在草稿引用中；每段复核的证据 ID 只能来自该段实际引用，
不能用其他已读或未读证据替引用补支持。不通过的段落必须提供有界缺陷说明。
Python 验证完整性、布尔标签、引用集合和大小限制，按标签计算是否通过，不根据
“如果/只有”等词汇猜测语义。覆盖项是否完整、标签是否正确仍需真实任务审核。

执行事件仅记录 draft/review 的动作码与通过、修订、拒绝等状态，不记录草稿、复核
反馈、证据正文或内部推理。反馈仅在当前请求内用于补救。
